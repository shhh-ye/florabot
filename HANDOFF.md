# Handoff — Florabot, ветка `claude/rag-system-integration-lgnn99`

Документ для нового чата: что сделали, почему так, и что осталось.

## Контекст проекта

Florabot — ИИ-бот цветочного магазина (Telegram + Instagram Direct).
Принимает сообщения, отвечает как продавец-консультант, при необходимости
смотрит цены/наличие в Google Таблице. Деплой — бесплатный Render.com.
Владелец — новичок, поэтому код и README максимально разжёваны на русском.

Изначально бот был одним файлом `app.py`: вебхуки + вызов OpenAI + поиск по
Google Таблице. Базы знаний не было — модель отвечала «из головы».

## Что просили

1. Ввести RAG-систему, как советовал ChatGPT (два md-файла с советами были
   приложены): документы → чанки → embeddings → векторная база → перед каждым
   ответом достаём похожие фрагменты и подставляем в контекст.
2. Отдельно возник вопрос: таблица часто обновляется — RAG будет отдавать
   актуальные цены? Нужна информация в реальном времени.
3. Разобрать плюсы/минусы вариантов, выбрать между «1» и «2».
4. Реализовать выбранный вариант — **«вариант 2, сделанный правильно»**.

## Что сделали и почему

### 1. RAG-архитектура (коммит 8ea7f41)

Разбили монолитный `app.py` на модули (`bot/`), потому что RAG — это несколько
шагов, и держать всё в одном файле новичку невозможно поддерживать.

- `bot/rag/chunker.py` — режет документы на фрагменты (по абзацам, с
  перекрытием). Перекрытие — чтобы мысль на границе фрагмента не терялась.
- `bot/rag/store.py` — ChromaDB (`PersistentClient`, cosine) + embeddings
  через OpenAI (`text-embedding-3-small`, батчами по 100). ID фрагмента —
  sha256 от содержимого → `upsert` не плодит дубли при переиндексации.
- `bot/rag/indexer.py` — собирает документы из `knowledge/*.md,txt` и из
  Google Таблицы, строит индекс. `ensure_index()` строит индекс при старте
  сервера, если он пустой — **потому что на Render диск эфемерный**, после
  каждого деплоя `.chroma/` пропадает.
- `bot/rag/retriever.py` — под вопрос клиента достаёт top-K (по умолчанию 6)
  фрагментов и форматирует их для промпта.
- `bot/memory.py` — история диалога с каждым чатом (`deque`, потокобезопасно).
- `bot/config.py` — вся конфигурация из переменных окружения. Google Таблицу
  сделали **необязательной** (раньше падало без неё).
- `app.py` стал тонким слоем вебхуков; логика ответа — в `bot/llm.py`.

### 2. Ключевое решение: цены НЕ индексируем (коммит 68b4c38)

Это и есть «вариант 2, сделанный правильно» — суть всего проекта.

**Проблема:** RAG-индекс — это снимок. Если положить в него цены и остатки,
они устареют, как только продавец поменяет число в таблице. А таблица меняется
часто. Бот назвал бы клиенту старую цену.

**Почему не «вариант 1» (вообще без индексации таблицы):** тогда теряется
умный семантический подбор («что-нибудь романтичное до 3000 ₽») — по живому
substring-поиску так не найдёшь.

**Решение — разделить данные по волатильности:**
- **Стабильное** (название, описание, повод, цвет, стиль) → идёт в RAG-индекс,
  даёт умный подбор.
- **Волатильное** (цена, наличие, остаток, скидка) → в индекс НЕ попадает.
  Бот всегда читает эти цифры из таблицы живьём, инструментом
  `search_google_sheet`, в момент ответа.

Реализация — на трёх уровнях, чтобы гарантированно не соврать:
1. **Структурно:** `indexer._is_volatile_column()` выкидывает волатильные
   колонки при индексации. Список колонок — `SHEET_VOLATILE_COLUMNS` в конфиге
   (цена/наличие/price/stock/… — по подстроке, без регистра). Физически цифры
   в индекс не попадают.
2. **В самом фрагменте** — приписка: «актуальную цену и наличие узнавай ТОЛЬКО
   через search_google_sheet».
3. **В системном промпте и описании инструмента** — жёсткое правило: перед тем
   как назвать цену/наличие, ОБЯЗАТЕЛЬНО вызови `search_google_sheet`, никогда
   не называй цифру по памяти.

Про стоимость важно (была путаница у владельца): вариант 2 **не дороже и не
медленнее** варианта 1 — живой вызов инструмента за ценой есть в обоих, а
RAG-запрос происходит на каждое сообщение в любом случае.

### 3. Укрепление после анализа репозитория (третий коммит)

По итогам анализа починили то, что дёшево и реально стреляет:
- **Фильтр эха Instagram** (`app.py`) — IG шлёт вебхук и на исходящие
  сообщения самого бота; без проверки `is_echo` бот отвечал бы сам себе.
- **Дедупликация повторных доставок** (`app.py`) — Telegram/Meta повторяют
  вебхук, если не получили 200 вовремя (а наш ответ занимает секунды);
  помним последние update_id/mid, чтобы не ответить клиенту дважды.
- **Лимит tool-цикла** (`bot/llm.py`, MAX_TOOL_ROUNDS=5) — страховка от
  зацикливания модели на вызовах инструмента; на последнем круге
  `tool_choice="none"` принуждает к текстовому ответу.
- **Разрезание длинных ответов** (`bot/channels.py`) — Telegram не принимает
  >4096 символов; режем по абзацам.
- **Защита чанкера** от вечного цикла при `CHUNK_OVERLAP >= CHUNK_SIZE`.
- **`hmac.compare_digest`** для сравнения секрета вебхука.
- **README**: старт-команда `gunicorn app:app --timeout 120 --threads 4`
  (дефолтный таймаут 30с убивал бы долгие ответы) + предупреждение НЕ
  увеличивать число воркеров (история диалога в памяти процесса).
- **Тесты переехали в репозиторий** (`tests/test_core.py`,
  `tests/test_volatile.py`) — работают без сети и настоящих ключей.

Сознательно НЕ делали: кэш Google Таблицы (меняет контракт «цены живьём» —
обсудить с владельцем, станет актуально при росте трафика или больших
каталогах из-за квот API).

### 4. Фоновая обработка вебхуков (четвёртый коммит) — после инцидента

Бот на Render умер после деплоя: генерация ответа (RAG + GPT-4o +
обязательный поход в таблицу за ценой на медленном бесплатном CPU) стала
занимать >30 секунд, gunicorn с дефолтным таймаутом убивал воркер посреди
ответа, Telegram повторял доставку — воркеры гибли по кругу (в логах
бесконечный WORKER TIMEOUT; «Perhaps out of memory?» — вводящая в
заблуждение стандартная приписка gunicorn, память была в норме).

Фикс: вебхуки отвечают мессенджеру 200 сразу, а ответ генерируется и
отправляется в фоновом потоке (`_reply_in_background` в `app.py`). Теперь
таймаут воркера в принципе не может убить обработку сообщения. Владельцу
также рекомендовано поставить в Render Start Command
`gunicorn app:app --timeout 120 --threads 4` (как в README).

## Что осталось / открытые вопросы к владельцу

1. **Реальные колонки таблицы.** Мы не знаем, как реально называются колонки
   в его Google Таблице. Для сильного семантического подбора нужна колонка с
   описанием/поводом/стилем. Если её нет — подбор будет слабым. Стоит спросить
   и при необходимости поправить `SHEET_VOLATILE_COLUMNS`.
2. **Документы в `knowledge/`** — там лежат ПРИМЕРЫ (faq/dostavka/uhod).
   Владелец должен заменить их на реальную информацию магазина и запустить
   `python scripts/index_knowledge.py`.
3. **Маршрутизатор запросов** — следующий шаг архитектуры (советовал ChatGPT):
   определять тип запроса (подбор букета / доставка / жалоба / заказ) и искать
   знания только нужной категории. Категория УЖЕ сохраняется в метаданных
   индекса, так что фундамент готов. Владельцу предлагали — ждём его решения.
