# Журнал отладки: «бот не отвечает» — все попытки и результаты

Хронология борьбы с молчанием бота на Render. Каждая итерация: симптом →
гипотеза → что сделали → что показал результат. Версии кода видны на
health-странице `/` (метка BUILD_MARKER).

---

## Инцидент 1 — 3 июля: бот умирает в цикле перезапусков

**Симптом.** После деплоя RAG-версии бот перестал работать. В логах
бесконечно: `WORKER TIMEOUT (pid:...)` → `SIGKILL! Perhaps out of memory?`
→ новый воркер → снова смерть через ~31 секунду.

### Попытка 1.1 — фоновая обработка вебхуков (коммит 2c80a72)

- **Гипотеза:** генерация ответа (RAG + GPT-4o + Google Таблица) занимает
  больше 30с; gunicorn с дефолтным таймаутом убивает воркер посреди ответа;
  Telegram, не получив 200, повторяет доставку — воркеры гибнут по кругу.
- **Фикс:** вебхук отвечает мессенджеру 200 мгновенно, ответ генерируется
  в фоновом потоке. Плюс рекомендация: Start Command
  `gunicorn app:app --timeout 120 --threads 4`.
- **Результат:** частично. Владелец поменял Start Command, но воркеры
  продолжали гибнуть даже со 120-секундным таймаутом — значит, что-то
  висло дольше 2 минут. Причина оказалась глубже.

### Попытка 1.2 — убрать ChromaDB (коммит 7f9ff11, параллельная сессия)

- **Гипотеза:** ChromaDB с зависимостями съедает сотни МБ из 512 МБ
  бесплатного тарифа — воркеров добивает OOM; плюс индексация при импорте
  ходит в сеть и не укладывается в таймаут старта.
- **Фикс:** ChromaDB заменена на индекс в памяти + JSON-файл (фрагментов
  десятки, качество то же — векторы те же, от OpenAI); индексация
  перенесена в фоновый поток; таймауты на все внешние запросы
  (OpenAI 60с, Telegram/Sheets 20с).
- **Результат:** бот ожил и отвечал. Инцидент 1 закрыт.

## Инцидент 2 — 5 июля: бот видит сообщения, но не отвечает

**Симптом.** «Написал ему привет, а ответа нет». В логах видно входящее
событие Telegram и... больше ничего. Иногда бот отвечал, иногда нет —
без каких-либо изменений в коде.

### Попытка 2.1 — v4: прозреть логи + предохранитель (merge e348db3)

- **Улика:** строка «RAG-индекс построен: 13 фрагментов» дважды появлялась
  в логах через МИКРОСЕКУНДЫ после «Shutting down: Master». Дважды подряд
  такое совпадение невозможно → вывод из фоновых потоков застревает в
  блочном буфере пайпа и вываливается только при смерти процесса.
  **Мы были слепы: часть логов не видна, пока процесс жив.**
- **Фикс:** построчный сброс stdout/stderr; пошаговые логи генерации с
  таймингами (`начинаю ответ → RAG за Xс → модель за Xс → ответ готов`);
  жёсткий дедлайн на генерацию (REPLY_DEADLINE=120с) — не уложились или
  упали → клиенту уходит извинение вместо тишины; max_retries=1 на
  OpenAI-клиентах (скрытые ретраи SDK не входят в timeout).
- **Результат:** логи ожили и сузили проблему. Новый лог показал:
  `ответ готов за 3.7с (finish_reason=stop)` — **генерация работает
  идеально**, а клиент ничего не получает. Значит, проблема в отправке —
  но отправка при успехе не логировалась вовсе (слепая зона ровно на
  подозреваемом).

### Попытка 2.2 — v5: диагностика отправки (merge 8961128)

- **Гипотеза:** умер TELEGRAM_BOT_TOKEN. Приём сообщений работает даже с
  мёртвым токеном (Telegram сам их пушит), а отправка — нет: классический
  симптом «сообщения приходят, ответы не уходят».
- **Фикс:** логировать КАЖДУЮ отправку (`✓ Отправлено` / `✗ ОШИБКА` с
  телом ответа API); самопроверка при старте: getMe (жив ли токен) +
  getWebhookInfo (последняя ошибка доставки по мнению самого Telegram).
- **Результат:** гипотеза про токен НЕ подтвердилась —
  `Telegram-токен OK: бот @Flora2026Bot`, вебхук зарегистрирован,
  pending_update_count: 0. Но новый лог дал следующую улику: после
  `ответ готов за 3.7с` — тишина 2+ минуты. Ни успеха, ни ошибки при
  таймауте 20с. Отправка виснет так, что таймаут requests не срабатывает.

### Попытка 2.3 — v6: отправка с повторами (merge 82789f3)

- **Гипотеза:** requests.post зависает на этапе, который таймаут requests
  не покрывает (например, DNS). Нужны повторы с жёстким потолком на
  каждую попытку.
- **Фикс:** до 3 попыток отправки; каждая в потоке из пула с потолком
  30с; зависшая бросается; 4xx (кроме 429) не повторяются; лог входа
  в отправку (`→ Отправка в Telegram (попытка N)...`).
- **Результат:** ДЫМЯЩИЙСЯ ПИСТОЛЕТ. Лог 23:36—23:37:
  - при старте getMe к api.telegram.org отработал за 0.3с — сеть живая;
  - через 13 секунд POST sendMessage на тот же хост завис;
  - все 3 попытки убиты ровно по 30.000с потолком, таймаут requests (20с)
    не сработал НИ РАЗУ, брошенные потоки молчали даже спустя 15 минут.
  - **Диагноз:** зависание ниже уровня HTTP-таймаутов — системный
    DNS-запрос (getaddrinfo), который таймаутами requests не покрывается.
    На бесплатном Render резолвер периодически умирает именно так.
    OpenAI при этом резолвился нормально. Это же объясняет «то отвечает,
    то нет»: мигающий резолвер.
  - Побочное открытие: зомби-потоки зависших попыток забивали бы пул —
    после 8 зависаний отправка встала бы навсегда.

### Попытка 2.4 — v7: тёплое соединение (merge b0281fb) — ТЕКУЩАЯ

- **Гипотеза:** если не резолвить api.telegram.org на каждую отправку,
  зависший DNS перестаёт быть участником процесса.
- **Фикс:**
  1. Общая requests.Session с keep-alive: проверка токена при старте
     прогревает соединение, отправка идёт по нему же — без нового DNS.
  2. Каждая попытка отправки — в собственном потоке (не в пуле):
     зомби не блокируют новые отправки.
  3. SEND_RETRIES=5 с растущими паузами (2с, 4с, 8с...) — если DNS
     всё же понадобился и лежит, у него есть ~2 минуты ожить.
- **Результат:** ожидает проверки владельцем. Проверка: на `/` метка
  «v7 — тёплое соединение с Telegram», в логах после сообщения должно
  быть `→ Отправка в Telegram (попытка 1)... ✓ Отправлено в Telegram`.

### Заготовленный план 2.5 — если v7 не поможет

Прибить IP-адреса api.telegram.org в обход системного резолвера
(резолвить самостоятельно с кэшем/фолбэком на известные IP Telegram).
Применять только если в логах v7 все 5 попыток виснут даже при
прогретом соединении.

## Уроки

1. **Сначала сделай логи честными, потом диагностируй.** Половина времени
   ушла на борьбу с невидимыми (буферизованными) логами. flush=True /
   line_buffering — с первого дня.
2. **Таймауты HTTP-библиотек не покрывают DNS.** `timeout=20` у requests
   не спасает от зависшего getaddrinfo. Потолок времени надо ставить
   снаружи (отдельный поток + join с таймаутом).
3. **Логируй успех, а не только ошибки.** «Нет ошибки в логе» ≠ «всё
   работает»: успешная отправка не логировалась, и слепая зона оказалась
   ровно на сломанном шаге.
4. **Клиент никогда не должен получать тишину.** Дедлайн + запасной ответ
   («отвечаю медленнее обычного») превращают загадочный отказ в понятное
   поведение.
5. **Диагностика по шагам с таймингами** (`начинаю → RAG → модель →
   отправка → доставлено`) позволяет по одной последней строке лога
   сказать, где именно завис бот.
